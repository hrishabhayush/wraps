The full flow

Every request, in order

Endpoint names for the SDK, issuer and merchant are our design. redeemVoucher() and /record-redemption come from Mastercard's AP4M guide.

Step 1

The agent checks the issuer before it trusts it

The issuer creates its keys inside the enclave. The Nitro hardware signs a receipt that names the exact code and both public keys. The SDK refuses to continue if any check fails.

Real AWS hardwareThe certificate chain leads to AWS's Nitro root certificate.
Nobody edited the receiptThe receipt's signature is valid.
Our exact codeThe code hash (PCR0) matches the published open-source build.
Not in debug modeThe hashes are not all zeros. In debug mode the operator can read memory.
Keys not swappedThe receipt's key hash matches the signing key and the payout wallet.
Fresh, not replayedThe nonce in the receipt matches the one the SDK just sent.
Step 2

Blind signing: the issuer signs what it cannot see

The SDK puts each token ID in a sealed envelope before it goes to the issuer. The issuer signs through the envelope. The SDK opens it and gets a valid signature on a token the issuer never saw.

Steps 3 and 4

Buying data, then settling later

Merchant asks for paymentIt answers 402 with a price in whole tokens. The SDK checks the price against caps set in code. The model cannot change them.
Agent pays with tokensIt repeats the request with Authorization: PrivateToken token=….
Merchant checks the signatureWith the issuer's public key. Under a millisecond, no network call.
Issuer checks the spent listThe merchant sends only the tokens and its ID. The issuer learns "2 tokens spent here, now," never whose.
Running total goes upLike a bar tab. The merchant's total rises from $4.10 to $4.30, and it gets the data out right away.
Settlement at fixed timesThe issuer signs an AP4M voucher for each merchant's total and redeems it. RLUSD lands at the merchant. Everyone's spending is mixed in one payout.

Limits

What is guaranteed, and what is managed

Guaranteed by math or hardware

  • The issuer cannot link a token to the agent it was issued to.
  • Nobody can forge tokens without the key inside the enclave.
  • A token cannot be spent twice. One spent list covers all merchants.
  • Nobody can swap the issuer's code or keys without the check failing.

Managed, not solved

  • Timing can link top-ups to spending when few people use it. This improves with more users.
  • The AWS host sees network timing. The enclave hides data, not traffic patterns.
  • Merchants see the agent's IP until the relay add-on ships.
  • An agent can reveal itself through logins or API keys.
  • RLUSD has clawback. We keep the pool small and offer XRP settlement.
